## Comments

- **Coach, one module + schema + example per section** (ticket 10's pattern; no edits to ticket 10's modules): `features/web_setup_exercises.py` (part `exercises`, view `setup/exercises`, `POST setup/exercises/classify {exercise_id, classification}` → chat's `classify_exercises`, `POST setup/exercises/pause {exercise_id, paused, reason?}` → `set_exercise_paused`), `web_setup_context_notes.py` (`context_notes`, `setup/context-notes`, `POST setup/context-notes/add {text, applies_from, applies_to?, tags, suggest_unusable?, exercise_id?}` → `add_context_note`, `POST setup/context-notes/delete {id}` → `delete_context_note`), `web_setup_profile.py` (`profile`, `setup/profile`, `POST setup/profile {patch}` → `update_coach_profile`), `web_setup_measurements.py` (`measurements`, `setup/measurements`, `POST setup/measurements/waist {cm, date?}`). Schemas `web_setup_{exercises,context_notes,profile,measurements}.schema.json` (+ examples). All commands return the section's view; all run through `web_setup.run_tool` (tool input schema, then the tool; refusal → 400 with the tool's reason).
- **None of these need an active phase** (chat's tools don't either), so they are not gated by `require_editable`.
- **Context notes:** chat stores the user's message as the note's text (`coach.current_message`); the web command sets it to the stripped `text` for the tool call and clears it afterwards. `suggest_unusable` (the model's judgement in chat) defaults to "no"; the form offers No / Maybe / Yes. List is every note, newest `applies_from` first; `tag_options` comes from `context_note.schema.json`.
- **Waist:** waist isn't a chat tool but a text handler, so its code was split in `features/measurements.py`: `waist_problem(cm)` (the range check and its words) and `add_waist(coach, cm, day, now)` (the insert), used by chat and the web. Reason on the web: "84 cm doesn't look like a waist measurement (40–200 cm)." (chat appends its own hint, 'send it in cm, e.g. "waist 84.5"', unchanged). The web may give a past `date` (default today, never in the future; `views.day` rules). `_received_since` became public `received_since` (used for "next due").
- **Photos read-only:** `Coach.photo(set_date, number) -> bytes` (core method, 404 `WebError` "There is no such photo.") looks the file up only through the `photos` table, by set date and 1-based position, and only inside `state/coach/photos` (no path from the request reaches the filesystem). `web_adapter.py` serves it at `GET /api/coach/photos/<date>/<n>` (`image/jpeg`, `Cache-Control: private`, `nosniff`), registered before the generic GET. Logs: the coach's web server has no access log; a failing photo read logs only the exception type, never a path or bytes. Note: `fa-api`'s own uvicorn access log still prints request lines (e.g. `GET /api/coach/photos/2026-11-09/1`), as for every `/api/coach/` call; dates only, no content. The adapter route was checked by hand with Starlette's TestClient (200 + bytes, 404 for an unknown photo, `..` paths fall to the generic 404), as the spec says the adapter isn't unit-tested.
- **Exercises:** the list is chat's `get_tracked_exercises` window (16 weeks), alphabetical, split on the page into Counting / Not counted; "not classified yet" shows (counts by default). Classification from the web stores reason "set on the web page". Ticket 09 plans lift-detail controls for the same tools; those should reuse these commands or the same tools (no shared code to conflict).
